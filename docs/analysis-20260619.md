## 1. Direct Conclusions

1. Ohara is already a sophisticated hybrid memory engine, not a starter project. It ships as a single static Go binary built with `go build -trimpath -ldflags "-s -w"` for linux/darwin on amd64/arm64. It has only three direct modules: `mark3labs/mcp-go`, `pkoukk/tiktoken-go`, and `modernc.org/sqlite v1.45.0`. It implements FTS5 plus optional Ollama embeddings, fuses lexical and vector retrieval with Reciprocal Rank Fusion at `k=60`, uses a five-state memory lifecycle, has a typed relation graph, persists post-write jobs in `memory_jobs`, and exposes a 33-tool MCP surface.

2. The core constraints are currently satisfied and should be defended: small footprint, single compiled binary, and comparable performance. The CI matrix builds four OS/arch targets in under 10 minutes. The runtime model is one binary plus one SQLite WAL database. Existing internal benchmarks already exceed the stated SLOs: Retrieval Fixture FTS5 mode has Recall@3 `0.966`, MRR `0.900`, nDCG@5 `0.914`, p95 `35.5 ms` across 70 cases; LongMemEval-style mode has Recall@3 `0.967`, MRR `0.970`, nDCG@5 `0.967`, p95 `37.2 ms` across 30 questions.

3. Ohara occupies a rare 2026 design quadrant: `local single binary + hybrid lexical/vector retrieval + relation graph + lifecycle`. Systems with comparable memory capability density tend to be cloud-hosted, Python-heavy, multi-process, or backed by Neo4j/Postgres/vector services. PROJECTMEM and Codified Context stay simpler by avoiding vectors and graph machinery.

4. The highest-value differentiation path is `local single binary + bi-temporal knowledge graph`. That quadrant is effectively empty. Ohara can move toward it without breaking constraints by adding temporal columns and entity tables inside SQLite instead of introducing Neo4j or a second daemon.

5. Deferred work in `docs/BENCH_COVERAGE.md` deserves re-evaluation. TKG entity graph and RL-bandit scoring were deferred for lack of evidence, but newer public results make temporal graph memory more compelling: Zep reports DMR `94.8%` versus MemGPT `93.4%`, and large-context BEAM-style results show no architecture saturates the 10M-token regime. Ohara still lacks official public LongMemEval, LoCoMo, and BEAM measurements.

### 2.2 Architecture Summary

Inputs: Claude Code, OpenCode, Gemini CLI, or any MCP client.

Runtime layers: CLI, Go binary, MCP stdio server with 33 tools, HTTP `/mcp` on port `7331`.

Database: `engram.db` in WAL mode.

Storage tables and concepts:

- `observations` plus `observations_fts` for BM25/FTS5 lexical retrieval.
- `obs_embeddings` storing embedding BLOBs for optional vector search.
- `memory_relations` for typed links: `caused`, `resolves`, `supersedes`, `related_to`, `implements`, `contradicts`.
- `entities` for entity-centric memory structure.
- `memory_jobs` as a durable post-write job queue.
- `sync_mutations` as an append-only mutation log.
- Memory lifecycle states: Active, Candidate, Superseded, Archived, Expired.

Consistency note: one generated visual summarized the relation graph as five relation types, but the implementation list contains six relation types: `caused`, `resolves`, `supersedes`, `related_to`, `implements`, `contradicts`.

### 2.3 Retrieval Pipeline

Ohara exposes three retrieval modes and resolves them at query time.

`fts5` is the default. It performs pure FTS5 search over `observations_fts` using BM25, then applies composite pack scoring: recency boost, utility weight, kind priority, classification weight, structural/relation weights, stale penalty, superseded penalty, and expiry penalty.

`hybrid` uses an FTS5 lane plus a vector cosine lane. Results are fused with Reciprocal Rank Fusion at `k=60`. The fusion also adds a lexical bonus when an item appears in both lanes and a lexical-score bonus proportional to BM25 rank. The vector lane reads `obs_embeddings(obs_id, embedding BLOB, model, created_at)` and uses Ollama through `embedTextOllama`; the default embedding model is `nomic-embed-text` with dimension `768`. Dimension mismatch warnings are emitted if the model changes.

`auto` probes the embedding backend with a `1.5 s` healthcheck. If Ollama is reachable, Ohara selects `hybrid`; otherwise it falls back to `fts5`.

Final hybrid score: `RRF_score + lexicalBonus + hybridScoreModifiers(item)`. Modifiers include a utility multiplier and kind-specific bonuses for `decision`, `procedure`, `pattern`, and `bugfix` memories.

### 2.4 Memory Hygiene Already Implemented

- Bi-temporal-ish observation fields: `created_at`, `updated_at`, `last_seen_at`, `expires_at`, and soft `deleted_at`; summaries have `valid_from / valid_to` semantics.
- `topic_key` upserts with `revision_count`.
- Rolling-window dedupe through `normalized_hash`.
- Conflict detection at save and read time: title Jaccard >=0.6, body TF-IDF cosine >=0.3, or embedding cosine when hybrid is enabled.
- Structural relation weights in pack scoring, including `supersedes=0.032`, `resolves=0.030`, and `implements=0.026`.
- Lifecycle decay and auto-archive: utility decay `0.9x` for memories older than 90 days, candidate archive after more than 30 days unreviewed, low-utility archive below `0.05`, and protection for foundational memories.
- Actor-aware writes: `user`, `agent`, `consolidation`, `import`, `system`; retrieval can down-weight inferred facts.
- Outcome tracking: success/failure counts feed `outcome_boost`.
- Secret redaction at plugin and store layers: `<private>` tags plus regex-based GitHub/OpenAI token stripping.

### 2.5 Actual Gaps

- TKG entity graph: deferred due to `no evidence of need` in benchmark coverage notes.
- RL-informed bandit scoring: deferred due to `no empirical gap`.
- Native in-DB vector index: not implemented. Vectors are stored as BLOBs and similarity is computed in Go memory. This is acceptable around `~1k` memory items but remains linear in `N`.
- In-db ANN: no HNSW/IVF; brute force only.
- Reranker: hooks exist, but shipped backends are TF-IDF and Ollama only.
- Public benchmark coverage: no official numbers yet for LongMemEval 500-Q, LoCoMo, or BEAM.
- Episodic-to-semantic consolidation: heuristic only; no A-MEM/MIRIX-style adaptive consolidation.
- Multi-user isolation: absent by design because Ohara is local-first and single-user.

## 3. Modern Agent-Memory Ecosystem, 2024-2026

The relevant comparison axis is memory representation, because representation largely determines whether a system can stay inside Ohara's constraints.

### 3.1 Ecosystem Positioning

| Representation / deployment | Cloud or multi-process | Local but not single binary | Local single binary |
|---|---|---|---|
| Plain text / event-sourced | PROJECTMEM, Codified Context | Usually Python-hosted | Empty or minimal systems |
| Lexical BM25/FTS5 + vector hybrid | Mem0/Mem0g, MemMachine, Hindsight, Stash | Letta/MemGPT, A-MEM, HippoRAG 2 | Ohara, Engram |
| Temporal knowledge graph + LLM extraction | Zep/Graphiti, Cognee | Heavy Python/Neo4j/Postgres stacks | Empty; Ohara can move here with a bi-temporal SQLite layer |

The original ecosystem visual placed Ohara and Engram in the local single-binary hybrid quadrant. It placed the target opportunity to the right: local single-binary temporal KG. That zone was marked as empty.

### 3.2 Vector-First with LLM Extraction: Mem0 Family

Mem0 extracts facts from each turn with an LLM call, vector-indexes them, and uses a second LLM call to choose ADD / UPDATE / DELETE / NOOP against the top-s most similar memories.

Public headline numbers cited in the source material:

- April 2026 algorithm: LoCoMo `91.6`, LongMemEval `93.4`, BEAM-1M `64.1`, BEAM-10M `48.6`.
- Token and latency profile: approximately `6.8k tokens/query`, p50 latency `0.88-1.09 s`.
- Original paper: Mem0 base approximately `66.9` LoCoMo J-score; Mem0g graph approximately `68.4`, about `+1.5` points.
- Structural cost: at least two LLM calls per turn on the hot path: extraction plus update classification. This prevents Mem0 from being a self-contained Go binary.

### 3.3 Temporal Knowledge Graph: Zep / Graphiti

Zep is the canonical TKG agent-memory comparison. It uses hierarchical subgraphs: episode, semantic entity, and community. Its model is bi-temporal: timeline `T` is world time, and timeline `T'` is transaction time.

Public headline numbers cited in the source material:

- DMR benchmark: Zep `94.8%` versus MemGPT `93.4%`.
- LongMemEval: up to `18.5%` accuracy improvement and `90%` latency reduction versus baseline.
- Cost: Cypher over Neo4j, 1024-dimensional entity embeddings, and LLM entity extraction with reflexion-style validation.

The useful idea to copy is not Neo4j. It is the bi-temporal representation: every fact carries when it was true in the world and when the system learned it.

### 3.4 Virtual Context Paging: MemGPT / Letta

MemGPT treats the LLM as an OS that pages memory blocks in and out through function calls. Letta evolved into a hosted platform and introduced sleep-time compute in April 2025, where agents use idle time to consolidate and rewrite memory. ICLR 2026 sleep-time compute work formalizes offline consolidation beyond inference-time scaling.

### 3.5 Agentic / Zettelkasten: A-MEM

A-MEM dynamically organizes memories through principled Zettelkasten: LLM-generated notes, dynamically generated links, and memory evolution where new notes update prior notes. It is Python-first.

### 3.6 Neurobiological: HippoRAG / HippoRAG 2

HippoRAG 2 extracts triples with OpenIE, builds a knowledge graph, and uses Personalized PageRank as the retrieval primitive. Among top performers, it is unusual because it does not require a hosted vector DB at runtime, but it still requires LLM calls during graph construction.

### 3.7 Multi-Agent Memory: MIRIX

MIRIX uses six specialized memory components: core, episodic, semantic, procedural, resource, and knowledge vault. These are coordinated by a multi-agent framework. The stack is heavy and Python-centric.

### 3.8 Hybrid SQLite + RRF: Ohara / Engram / vstash / sqlite-rag

This is Ohara's quadrant. Engram is Ohara's parent project with the same Go + SQLite + FTS5 + MCP shape and MIT license. The broader pattern, SQLite FTS5 + sqlite-vec + Reciprocal Rank Fusion, is now mainstream enough that vstash was built around it. Mem0 also adopted multi-signal retrieval in its April 2026 algorithm: semantic + BM25 + entity scoring in parallel, fused afterward. That is structurally close to Ohara's RRF design.

### 3.9 Plain-Text Event-Sourced: PROJECTMEM

PROJECTMEM argues that embeddings are not always necessary. It stores project history as a typed event log and adds a deterministic pre-action gate that warns the agent before repeating a known-failed fix. It is Python-hosted and MCP-compatible.

## 7. Dependency Options for Native Vector Search

| Option | Pure Go | 1M vector viability | Verdict for Ohara |
|---|---|---|---|
| `modernc.org/sqlite/vec` | yes | unproven at 1M, fine at 100k | Recommended. Drop-in blank import next to existing `modernc.org/sqlite`; preserves no-CGO and single-binary shape |
| chromem-go | yes | no, ~4 GB RAM at 1M x 1024 | Acceptable below 100k items; loads vectors into RAM |
| Bleve | yes | marginal | Could replace FTS5 + vector in one library, but it is a larger refactor |
| sqlite-vec via `mattn/go-sqlite3` | no, CGO | yes | Reject. Breaks no-CGO portability |
| go-libsql / DiskANN | no, CGO | yes | Reject for this constraint set; no Windows and CGO |
| DuckDB + VSS | no, CGO | yes | Reject as overkill |

`modernc.org/sqlite/vec` is the only option that keeps the constraint envelope intact while enabling sub-linear ANN and SQL-joined hybrid queries.

## 8. Improvement Roadmap

### 8.1 Short Term, Weeks 1-3: Make Capability Legible

1. Run the official LongMemEval 500-question benchmark. The repo already has a `JudgeModel` interface and `ImportFromJSONL()`. Publish one number next to Mem0 `93.4` and Hindsight `91.4`.
2. Add LoCoMo and BEAM-1M harnesses using the same fixture pipeline. These are required comparison numbers in 2026 memory-system discussions.
3. Publish a stable `BENCHMARKS_RESULTS.md` comparing Ohara `fts5` and `hybrid` modes against Mem0/Zep on identical fixtures where possible.
4. Track binary size and dependency count in CI so the constraint envelope is measured on every PR.

### 8.2 Medium Term, Weeks 4-10: Add `modernc.org/sqlite/vec`

This is the highest-ROI change under the constraints. It replaces brute-force cosine over BLOBs with native `vec0` KNN without adding CGO or changing the runtime model.

1. Add `_ "modernc.org/sqlite/vec"` as a blank import beside the existing `modernc.org/sqlite` import.
2. Create a `vec0` virtual table beside `obs_embeddings`:

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS observation_embeddings_vec USING vec0(
  obs_id INTEGER PRIMARY KEY,
  embedding FLOAT[768],
  model_name TEXT,
  content_hash TEXT
);
```

3. Keep legacy `obs_embeddings` as a write-through table until `vec0` correctness is proven, then deprecate it.
4. Replace the in-Go cosine loop with a `vec0` KNN query as the right-hand lane of `fuseHybridRRF`. RRF math remains unchanged.
5. Keep brute-force fallback for deterministic-test and static-test embedders in CI.
6. Optional: add int8 quantization for `N > 50k`. Expected effect: about `4x` storage reduction, about `2x` scale speedup, small single-digit recall hit.
7. Backfill embeddings through the existing `memory_jobs` queue.

Expected performance: brute force at 1k items is already sub-millisecond and fixture p95 is dominated by FTS5, not cosine. Around 50k items, the cosine loop will dominate. `vec0` should push the practical crossover above roughly 1M items.

### 8.3 Medium-Long Term, Weeks 8-14: Add Bi-Temporal Layer on the Existing Relation Graph

Do this in Ohara/Engram style: no graph DB, no LLM on the hot path, additive to `memory_relations`.

1. Add `valid_from` and `valid_to` columns to `memory_relations`. This converts the static relation graph toward a bi-temporal model while staying inside SQLite.
2. Add an `entities` table with: `kind` (`person|project|file|tool|topic|service`), `canonical_name`, `first_seen_at`, `last_seen_at`.
3. Implement a deterministic entity extractor: regexes, capitalized terms, ISO dates, tool names, and URL hosts. This keeps retrieval-time LLM calls at zero.
4. Add MCP tools: `mem_temporal_state(entity, at=ISO_TIME)`, `mem_lineage(topic_key)`, `mem_supersedes(obs_id)`.
5. Add Allen-interval overlap boost to pack scoring: increase structural weight when a memory's validity window overlaps the query timeframe.
6. Optional: add an LLM relation classifier behind a flag, executed through `memory_jobs` only when Ollama is reachable. This can backfill `edges.relation` and entity `kind` lazily without putting the LLM on the hot path.

### 8.4 Longer Term: Constraint-Relaxing Ideas That Need Written Justification

| Idea | Inspiration | Utility | Constraint risk |
|---|---|---|---|
| Pluggable HNSW index | `coder/hnsw` pure-Go | Sub-linear retrieval at million scale | Only useful above ~50k items; `vec0` may be enough |
| Sleep-time consolidation | Letta sleep-time compute | Offline merge/dedupe of episodic memories | Requires local LLM availability, but can remain local with Ollama |
| Personalized PageRank reranker | HippoRAG 2 | Better multi-hop recall | Pure Go version is feasible and likely passes constraints |
| Embedded LLM extraction model | A-MEM / Mem0 | Higher recall for unstructured input | Reject unless constraints change; binary size blows up by ~100x |
| Postgres + pgvector backend | Stash | Multi-tenant scaling | Reject for core binary; breaks SQLite single-file model |
| Neo4j migration | Zep | Full graph capability | Reject for core binary; largest constraint violation |
| Built-in cloud sync | Mem0 cloud | Cross-machine memory | Should live in a sibling repo, not the core binary |

### 8.5 Explicit Non-Goals

- Do not bring in `sqlite-vec` through `mattn/go-sqlite3`; CGO breaks portability and the no-CGO architecture rationale.
- Do not migrate to a graph database; a second daemon kills the single-binary design.
- Do not add LLM calls to the hot path; `zero LLM at retrieval time` is a differentiator.
- Do not delete `topic_key` upserts, `normalized_hash` dedupe, or soft-delete `deleted_at`; graph/TKG additions must compose with them.
- Do not bundle an embedding model in the binary. `nomic-embed-text` is roughly 274 MB on disk, which would be a ~15x binary-size regression for marginal benefit. Keep Ollama optional and external.

## 9. First PR Sequence

1. `bench/longmemeval/official_500`: add official LongMemEval JSONL fixture loader and a CI job that publishes one number to README. Estimated cost: ~1 day.
2. `bench/locomo + bench/beam`: add LoCoMo and BEAM-1M harnesses using the existing `JudgeModel` interface. Estimated cost: ~3 days.
3. `ci/size-guard`: fail PRs that grow the stripped binary by more than 5 MB or add new direct dependencies without a label. Estimated cost: ~2 hours.
4. `feat(store): native vec0 virtual table`: add `_ "modernc.org/sqlite/vec"`, create `observation_embeddings_vec`, and dual-write from `indexMemoryEmbedding`. Estimated cost: ~1 day. Quality SLO unchanged.
5. `feat(store): vec0 KNN replaces in-Go cosine in hybrid RRF`: switch the right-hand lane of `fuseHybridRRF` to `SELECT obs_id, distance FROM observation_embeddings_vec WHERE embedding MATCH ?`. Remove brute force when `N > 1000`.
6. `feat(graph): add valid_from / valid_to to memory_relations`: migration plus backfill. No behavior change yet.
7. `feat(graph): entities table + zero-LLM extractor`: background job fills entities from observation content using regex/heuristics. Runs on `memory_jobs`; never blocks `mem_save`.
8. `feat(mcp): mem_temporal_state, mem_lineage, mem_supersedes`: add three MCP tools. Tool count rises from 33 to 36. Pure SQL and fully additive.
9. `feat(pack): Allen-interval temporal boost`: add a small `temporalOverlapBonus` term to pack scoring. This is the single most predictive feature from Zep-style temporal analysis.
10. `docs: update COMPARISON.md against Mem0/Zep/Letta`: replace claude-mem-only comparison with a multi-system table, including official benchmark numbers from commits 1-2.

## 10. Final Verdict

Ohara is, in this analysis, the most capability-dense agent-memory system that still fits a single static Go binary. Engram occupies a nearby quadrant but lacks Ohara's typed memory, conflict detection, relation graph, and lifecycle. Systems at Ohara's capability level usually require Python, Neo4j, Postgres, a hosted vector DB, or multiple of those.

The three constraints are not in conflict with the obvious next steps. `modernc.org/sqlite/vec` addresses the structural vector-search gap without CGO. The TKG item can be reopened as a SQLite-native bi-temporal relation layer rather than a Neo4j migration. That captures the useful part of Zep's model while preserving Ohara's design.

The next month should focus on public benchmark legitimacy: official LongMemEval, LoCoMo, and BEAM-1M numbers. Without those, Ohara is under-credited. With them, Ohara can credibly own the niche of serious agent memory under a strict single-binary constraint.
